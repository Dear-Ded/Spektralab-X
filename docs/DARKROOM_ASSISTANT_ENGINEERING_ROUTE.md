## D2. Android adaptation and cross-compilation

- **First implementation:** Kotlin inside the existing `advisor` package and existing native calls. No new C++ dependency, ABI, shader, broad native toolchain bump or dedicated metrics library. The current build is minSdk 29, arm64-v8a, NDK `27.2.12479018` with flexible page sizes and existing CMake/JNI pipeline. Use actual profiling before moving a proven hot loop to C++; if necessary, move just that loop and compare its output against the Kotlin reference before building Android with the same pinned NDK. Continue using the established upstream patch replay for changes to upstream files.
- **If semantics earns a pilot:** the official sample references `com.google.mediapipe:tasks-vision:1.2.2`. Google Maven POM directly lists `tasks-core:1.2.2` and `com.google.ai.edge.litertlm:litertlm-android:0.18.0`. The main AAR itself was 485,698 bytes and contained no matching `jni/arm64-v8a/*.so`; that says nothing about total dependency size or native alignment. Resolve the full Gradle release graph, inspect transitive AARs/merged APK and record actual size, bundled libraries, licenses and permissions. Do not strip declared transitives by guess. If packaged costs are excessive, evaluate a minimal LiteRT-only proof against the same pinned model and output contract instead of maintaining both integrations; otherwise leave semantics unshipped.
- **If a native dependency is later necessary:** consume a verified Android artifact when possible; only cross-compile source when a justified candidate requires it and the licensed source/toolchain can reproduce it. Check API 29 load, arm64 dependency/symbol closure, ELF LOAD and APK ZIP alignment, and the project's current packaging allowlist with the real APK. [Android's 16 KB guide](https://developer.android.com/guide/practices/page-sizes) covers prebuilt libraries too; our own linker flags cannot fix another AAR's prebuilt `.so`. No release exception or compatibility bypass for the experiment.

## D3. Own the analysis-to-edit boundary

1. **Analysis (`advisor/editor` and `advisor/domain`).** Extend `AdvisorStatisticsSampler` from the actual current-edit frame. Define a compact immutable scene-evidence value with frame identity, measurement domain/version, strip/region measurements and request-local references. Use post-crop image coordinates and explicit content bounds, not screen dimensions. Keep the old encoded sRGB Y' fields unchanged; document a physical or display-relative metric separately before adding it. Use one pass over a bounded grid for broad measurements, weighted sampling where needed, and a normal-preview region check for small important highlights. RAW/JPEG/HEIF and different cameras share this path when the frame and domain are supported. Never mislabel rendered endpoint observations as sensor clipping or assert unknown subject classes. The first reference region can be injected by a test fixture or an existing edit signal; a new picker is a separate UI decision.
2. **Decide (`advisor/session`, `advisor/domain`, existing `advisor/network`).** Serialize versioned evidence as optional request data, and only with permission for what is actually sent. Current stored/resolved values, absolute units, locks, ranges and allowed operations come from `ParameterRegistry` and the draft snapshot. Do not branch photographic policy by provider. Use the existing v2 scalar and v3 direction result modes; no new edit types or arbitrary mask coordinates in this phase. Distinguish no change, need input, unsupported, network failure and no verified candidate. A scene reference explains the suggestion; it is not permission to edit that shape.
3. **Render and verify (`AdvisorEditorPort` / existing engine).** Route proposals into existing `Edit` projection and draft controls, not into the decoder or a copied pixel pipeline. Hold crop, style, original, curve, locks and existing masks fixed. Verify the same baseline-selected target/protected pixels on the actual rendered preview. Reuse the published frame/ticket ownership checks and the cinematic verification pattern. Only the final accepted candidate reaches draft publication. Discard/undo/strength/save/export behavior must still use their existing authorities; a trial never lands in history/export. Where a working local mask is not available, a request for exact subject-only changes stays unsupported rather than being substituted with a broad edit.
4. **Optimize by measurement.** Baseline at the current sampler and one normal editor render. Measure area analysis and color conversion, engine switching/trial renders and model roundtrip separately, on cold and warm runs. Reuse the already-decoded frame and bounded buffers; do not trigger another full-resolution RAW decode or retain a duplicate image. If magnitude is the issue, prototype one target (lift midtones without disturbing highlights), two controls (exposure/highlights) and at most six additional unpublished reduced-size probes plus one normal-quality verification. Do not adopt the probe loop if it cannot both improve outcomes and meet the frozen device budget. If subject/context errors dominate, first try human labels as a ceiling, then compare MediaPipe. These are separate hypotheses, not fallback chains in the released app.

**Freeze before comparisons.** Start with at least 24 distinct licensed or self-collected photos (group variants by original) spanning ordinary daylight/landscape, portraits, night/mixed light, backlight, specular products and intentional low-key looks. Include both JPEG and supported RAW, at least two film looks with different strengths, and synthetic geometry/color tests. Freeze goals and protected regions before seeing results; include no-change and unsupported cases, and opposite intent on the same input. Review pairs blind at the same scale. Record wins, ties, losses and reasons (region, operation, strength, or unsupported). Require wins to exceed losses and no new critical loss on the protected set; retain every failure, repeat on untouched images before declaring general improvement. Chooser regions and metrics compare the same source, crop, style, domain and stage. Do not infer aesthetic correctness from one aggregate or cherry-picked screenshots.

**Repository practice.** At implementation start move this decision into version control under `docs/`; make the new scheme and units readable alongside code and put pure fixtures/unit cases in the existing test tree. Prefer a typed value and the existing registry/port over a generic plugin API, speculative abstraction or duplicate fallback path. Use focused commits/PRs for migration, evidence, model request and any external/native dependency separately. Keep source rev, model/license and checksums next to any admitted vendor change; retain modifications and notices rather than pasting untraceable snippets. Use current Gradle verification and upstream replay patterns where applicable, and do not introduce a new build tool to manage a single pilot. Store small test vectors in Git; put licensed larger image assets and raw reports outside Git with a manifest and an immutable result reference. CI and cloud can run reproducible host/Android jobs and comparisons; Android timing, storage and GPU results require the matching build on representative hardware. Do not report CI as live-provider or device acceptance. Public release notes describe only real user improvements, not internal environments or account details.
