# 更新说明怎么写 / How release notes are written

更新说明是写给用户看的，不是工单清单。参考哔哩哔哩那种画风：像一个有点话痨、有点爱玩梗的开发者，在暗房门口跟你唠这次又折腾了啥。

`CHANGELOG.md` 里每个版本的那一节会原样成为 GitHub Releases 页面的正文（`scripts/release-notes.sh`），所以写在这里就是写给所有下载的人。

## 语气

- **灵动、有梗、敢自嘲。** 可以拟人（“滑杆终于学会了听话”）、可以夸张（“颜色对得上到连像素都不好意思有分歧”）、可以吐槽自己（“上一版那条滑杆，属于是摆设界的天花板”）。
- **抽象一点没关系，但要让人一眼看懂。** 每个梗后面跟着它到底改了什么，玩梗不能把事实玩丢。
- **贴着胶片和暗房玩梗。** 显影、定影、安全灯、齿孔、过期胶卷、冲扫店老板，这些是我们自己的梗库，比通用网络热梗更有辨识度。
- **小标题也可以搞怪**，但要能看出这一节讲什么。
- **表情符号克制使用**，一节最多一两个，起点睛作用，不刷屏。

## 底线（再怎么搞怪也不碰）

1. **事实不变形。** 数字、默认值、兼容性、没做完的事，一个字都不夸大，一个都不藏。梗是包装，不是遮羞布。
2. **坦白区必须有。** “还没做好的 / 已知的坑”单独一节，照样可以写得有趣，但要写清楚。没在真机上验证，就明说。
3. **不嘲讽用户，不阴阳别的项目，不碰低俗、地域、政治梗。** 自嘲随便，调侃上游作者不行，感谢要真诚。
4. **不用营销腔**：不写“重磅”“全新升级”“极致体验”这种空话，搞怪要具体。
5. **不追会过时的热梗。** 一年后再看还能懂的才写。

## 结构（可以改名、可以加戏，但顺序大体保持）

```
## 版本号 · 日期

> 开场白：一两句，这一版是什么心情、什么来历。

### 头条（一到两件最重要的事，讲透）
### 新玩具（新功能）
### 顺手了 / 修好了
### 还没冲洗完的（已知问题、未验证）
收尾（感谢 + 欢迎来提 Issue）

<details><summary>技术细节（硬核区，可跳过）</summary> 精确、无梗的改动清单 </details>
```

技术细节区**不玩梗**，保持准确、可查，给想深究的人看。

## 商店短说明

`fastlane/metadata/android/*/changelogs/<versionCode>.txt` 有 500 字符上限。两三句同样画风的话，挑最重要的说，不列清单。

## 英文

英文版按英文的说话习惯重写，保留轻松的语气和自嘲，梗可以换成英文读者能懂的，不逐字直译。
