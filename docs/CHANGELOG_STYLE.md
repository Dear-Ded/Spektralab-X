# 更新说明怎么写 / How release notes are written

更新说明是写给用户看的，不是写给开发者看的。参考哔哩哔哩的更新说明：像一个人在跟你说这次改了什么，而不是一份工单清单。

`CHANGELOG.md` 里每个版本的那一节会原样成为 GitHub Releases 页面的正文（`scripts/release-notes.sh`），所以写在这里就是写给所有下载的人。

## 原则

1. **先说用户感受得到的。** 按"你会注意到什么"分组：变好看了、变顺手了、颜色更准了、修好了什么。不按代码模块分。
2. **说人话。** "拖滑杆不用重新冲洗，手指到哪画面到哪"，不写"Layer 2 在打包阶段应用，repack 路径不重跑引擎"。
3. **有温度，但不油腻。** 可以有一句开场、一句收尾，可以说"终于"、"这次有点大"。不堆表情符号，不写"宝子们"，不卖萌，不夸大。
4. **说实话。** 没做好的、还没在真机上验证的、已知的问题，单列一段写清楚。不把小改动包装成大更新。
5. **数字照写，但翻译成人话。** 比如"平均 ΔE00 0.000，差别小到肉眼看不出来"。
6. **技术细节放在最后折叠起来。** 用 `<details>` 收起，给想深究的人看，普通用户可以跳过。
7. **记得感谢。** 提了反馈的人、上游项目，有就写。

## 结构

```
## 版本号 · 日期

> 一两句开场：这一版是什么样的一版。

### 最想让你知道的（一到两件事，写透）
### 新功能
### 用起来更顺手 / 修好了
### 还没做好的
一句收尾（感谢、欢迎反馈）

<details><summary>技术细节</summary> 精确的改动清单 </details>
```

没有内容的小节就删掉，不要硬凑。

## 商店短说明

`fastlane/metadata/android/*/changelogs/<versionCode>.txt` 有 500 字符上限。写两三句同样语气的话，挑最重要的说，不列清单。

## 英文

英文版按英文的说话习惯重写，意思一致，不逐字直译。
