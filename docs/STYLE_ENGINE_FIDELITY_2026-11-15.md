# 风格与引擎还原修正

2026-11-15，GPT（OpenAI）共创。本轮修复已定位的参数继承、LUT 链路降采样和分享精度损失。目标是忠实执行已有配方与原始色表；没有改变胶片 / 相纸物理数据、上游固定引用、默认 RAW 开发方式、87 套审美参数或上一轮十款原创候选。代码属于下一版研究分支，已发布 Alpha 8 不受此提交影响。

## 1. 修正了什么

**内置风格使用完整物理基线。** 之前切换风格会继承前一个效果的预闪、染料耦合、散射、底片前曲线、测光方式和部分扫描 / 镜头参数。同名风格可能因操作顺序得到不同结果。现在 87 套内置风格先恢复共同物理基线，再应用各自原配方。导出内置风格时携带完整引擎设置，包含正片标志与颗粒 / 光晕 / 眩光启用状态。照片的 RAW 开发、RAW 曝光、裁切、旋转与局部蒙版继续保留；用户文件中省略的可选引擎字段仍遵循原有继承规则。

**新导入的 CUBE 保留原始求值链。** 旧代码先把 1D 整形与非单位定义域折进来源 3D 网格；来源只有 2³ 时，257 点非线性曲线会被压成两端点。现在兼容表直接从完整链烘焙到最终网格。对于原文不超过 12 MiB 的新导入，另用 SPK4 记录保存原文，并通过新增 `setSourceLutV1` 在原生 `SourceLut` 中直接执行 1D 线性插值、两套定义域、3D 四面体插值及原有色彩空间转换，消除这段中间网格近似。

纯 ProPhoto、单位定义域、无整形、边长不超过 65 的源表保留原来的直接查表路径。旧 SPKL / SPK2 / SPK3 缓存继续使用其已有烘焙结果，不自动改变旧照片。Hald 导入仍走原有烘焙路径。LUT 强度混合、Layer 2 顺序与 sRGB / ProPhoto 数值合同保持。

**原文按字节保留。** 12 MiB 以内的 CUBE 原文、原始色彩空间和兼容表一起原子提交。分享携带原文，避免六位小数再序列化和连续重采样。原文超过包内上限的独立 CUBE 仍可导入，但使用有限网格路径，分享携带最终 ProPhoto 表，以可往返 Float 文本保持该网格的数值；导入报告明确标注此限制。

## 2. 对照与数值结果

先在旧代码运行反例，再应用修复。`before/` 中两个整形 / 定义域测试均失败：例如输入 0.25 经平方整形应为 0.0625，旧路径得到 0.25。`builtin-before/` 的四项测试有两项失败，显示前一个效果的物理参数残留。最终这些测试全部通过。

独立参考使用解析生成的 257 点三通道曲线、非单位定义域和交叉通道仿射 2³ 表。Kotlin 参考以 Double 计算，输入与原始样本按 Float 合同读取；C++ 使用实际生产实现。每个色彩空间 16,384 个确定性离网格输入，共 32,768 个像素。以下为编码 RGB 通道绝对差，不能解释为 DeltaE、视觉差异阈值或所有照片表现。

| 路径 | sRGB 平均 / 最大差 | ProPhoto 平均 / 最大差 |
|---|---:|---:|
| 旧的先压缩到 2³ 再烘焙 | 0.0830527 / 0.297723 | 0.134787 / 0.327860 |
| 修正后的最终 65³ 兼容表 | 0.000153652 / 0.0279190 | 0.000138778 / 0.0210852 |
| 最终原生原始链求值 | 1.15717e-8 / 1.19209e-7 | 1.26032e-8 / 5.96046e-8 |

最终原始链在这批样本上的 16 位量化最大差为 1 个码值。独立测试还用 129³ 交替条纹表检查原生接口的所有 129 个红轴格点，细节全部保留。这是原生容量测试，**不代表超过 12 MiB 的独立文件也已绕过兼容网格**。

分享验证包括两种空间各三轮真实 `StyleImports` 读取 / 导出 / 重导入，以及五轮底层 SPK 包往返：原始字节、色彩空间、强度与兼容表 Float 值保持。超过包上限的反例验证回退表可以逐 Float 恢复，但不把回退表称为原始链无损。

## 3. 云端验证与计算成本

全部编译和可执行测试在 AOIDC 云端进行。本机只做源码、文档、Git、归档和哈希处理；未使用私人影像。IBX 当时处于免费实例冷却期，本轮没有等待它、购买实例或新增凭据。

- 完整 JVM：Debug 390 项、Release 241 项，均 0 失败、0 错误、0 跳过。包含上一轮中英文 20 个风格包的可选集成测试。87 套内置风格逐套验证前序状态独立、完整配方分享往返，以及照片参数保留。往返比较的是完整物理设置及精确解析后的渲染数组，不要求 UI 色盘初始位置元数据相同。
- 原生原始链与兼容表插值：各 32,768 像素，AddressSanitizer / UndefinedBehaviorSanitizer 通过。直接 JNI 测试覆盖强度 0 / 0.37 / 1、设置滑杆后保留 LUT、清除及无效定义域 / NaN / 超范围边长拒绝；拒绝不改变旧状态。
- 实际 JNI 与引擎预览：sRGB / Display P3 各五种路径，共十组；每组 393,216 字节与相同小输入的正式渲染逐字节一致，父会话状态和 RAW 所有权检查通过。此项关闭 Vulkan 驱动泄漏检测，地址及未定义行为检测继续启用；独立原始链与 JNI 状态测试启用泄漏检测。
- Android NDK 27.2 实际 ARM64 JNI 编译及共享库链接成功。复用未修改的其余对象与静态库，40 个导出与 Kotlin 编译产物的全部 native 声明匹配，新方法描述符为 `(J[F[FI[FZF)Z`，ELF LOAD 对齐至少 16 KiB。本轮没有构建或发布新的 APK，不能视为完整 APK 安装验收。
- 25 个相关实现、测试及依赖文件在云端与本机按字节哈希全部一致，见 `tested-source.json`。完整物理引擎和 LibRaw 静态库复用前次云端缓存，哈希记录在 `environment.json`；没有声称本轮重新构建整个上游或取得新的手机 GPU 一致性结果。

在其他测试结束后，使用同一宿主机、单线程、1,048,576 像素、三次重复测量，中位数如下。原始链的 sRGB 路径包含逐像素转移函数与矩阵，因此比预烘焙查表更慢。普通纯 ProPhoto 表继续走原来快速路径，不承担此项开销。

| 测试输入链 | 预烘焙 65³ | 原始链直接求值 |
|---|---:|---:|
| sRGB 整形 + 定义域 + 3D | 64.803 ms | 508.629 ms |

首次 JNI 测试脚本缺少 `input_transform.cpp` 等真实依赖，链接失败；补齐依赖后通过。一次 JVM 往返断言把色盘 UI 初始位置当作渲染差异，修正为完整物理字段与精确渲染值比较后，重新执行两变体全部测试通过。ARM 符号检查最初误计编译器内部符号、随后漏掉既有 private 方法，最终改为精确 JNI 前缀及 `javap -private`，核对 40 / 40；记录在 `abi.json`。失败过程留证，不计入最终成功数量。

## 4. 还原范围与复现

当前改进能证明配方执行稳定、原始 CUBE 在上述输入合同中按原样计算。厂商专有相机色彩、胶片乳剂、扫描仪校准仍缺同场景 RAW / 官方输出或标准色卡参照，不能据此宣称与厂商、胶片实拍或达人作品精确一致。曝光、白平衡、光照、镜头、局部光影与输入编码都会影响外观。内置风格的相同参数也不等于不同尺寸预览在颗粒 / 空间效果上逐像素相同。

sRGB 输入路径仍裁切超出 sRGB 的值；未自动识别 Rec.709、Log、PQ、HLG。独立 CUBE 最高 64 MiB，SPK 包内原文最高 12 MiB；大文件回退仍有有限网格误差。旧缓存若需本轮原始链修正，应从保留的原始文件重新导入。没有新增真机数据、相机全库、混合光、多肤色或长期热耗电验收。

公开证据目录：`docs/validation/style-engine-fidelity-2026-11-15/`。最终结果只取 `final-r2/`、`direct-native-r2/`、`jni-r2/`、`selection-r2/`、`arm64/` 与 `cost-final/`；`before/` 和 `builtin-before/` 是旧代码反例，`jni/` 与 `failed-final-jvm/` 是失败尝试。
